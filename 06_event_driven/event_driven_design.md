# Проектирование Event-Driven архитектуры: Фитнес-трекер

## 1. Анализ событий в системе

### Команды и соответствующие события
- POST /users → UserRegistered
- POST /exercises → ExerciseCreated
- POST /workouts → WorkoutCreated
- POST /workouts/{id}/exercises → ExerciseAddedToWorkout
- PATCH /exercises/{id} → ExerciseUpdated

### Потребители событий
- UserRegistered: сервис уведомлений (приветственное письмо), аналитика регистраций.
- ExerciseCreated: поисковый индекс справочника, аналитика популярных упражнений.
- WorkoutCreated: аналитика активности, аудит.
- ExerciseAddedToWorkout: пересчёт статистики, инвалидация кэша статистики (Redis из ДЗ 05).
- ExerciseUpdated: инвалидация кэша списка упражнений, обновление read-модели.

## 2. Проектирование Event-Driven архитектуры

### Производители событий
- Workout Service / Exercise Service / User Service (REST API на FastAPI в ДЗ 02–05; демонстрационный producer на C++ в этом каталоге). События публикуются после успешной фиксации данных в PostgreSQL.

### Потребители событий
- NotificationService: email-напоминания и отчёты по тренировкам.
- StatisticsProjectionService: обновление агрегатов для GET /users/me/workouts/statistics.
- CacheInvalidationService: сброс ключей Redis (exercises:list, stats:user:*).
- AuditService: журнал изменений для разбора инцидентов.
- AnalyticsService: метрики для дашбордов (число тренировок, топ упражнений).

### Структура события
Событие сериализуется в UTF-8 JSON и содержит:
- event_id — уникальный идентификатор события (UUID);
- event_type — тип события;
- timestamp — время возникновения (мс);
- aggregate_id, aggregate_type — идентификатор и тип доменного объекта;
- payload — данные, специфичные для типа;
- metadata (опционально): correlation_id, user_id инициатора.

### Поток событий
1. Клиент отправляет HTTP-запрос в API Gateway (Nginx).
2. Сервис валидирует данные и сохраняет их в PostgreSQL.
3. После коммита транзакции сервис публикует событие в Kafka.
4. Брокер распределяет сообщение по партициям.
5. Подписанные сервисы потребляют событие и выполняют асинхронную обработку.

## 3. Проектирование взаимодействия через брокер сообщений

### Выбор брокера
Используется **Apache Kafka**. Высокая пропускная способность, хранение истории для аудита, партиционирование по user_id сохраняет порядок событий одного пользователя.

### Формат сообщений
JSON в UTF-8. Эволюция схемы — через опциональные поля (обратная совместимость).

### Гарантии доставки
- **Публикация:** идемпотентный producer, `acks=all` — подтверждение от всех in-sync реплик.
- **Потребление:** at-least-once с ручным commit offset после обработки; дедупликация по event_id на стороне потребителя.

## 4. Применение паттерна CQRS

### Применимость
CQRS уместен: запись (создание тренировки, добавление упражнений) и чтение (история, статистика за период, список упражнений) имеют разную нагрузку и требования к индексации.

### Разделение моделей
- **Write Model:** нормализованная схема PostgreSQL (users, exercises, workouts, workout_exercises). Транзакционная целостность и публикация доменных событий.
- **Read Model:** денормализованные представления в Redis (кэш из ДЗ 05) и материализованные агрегаты статистики. Оптимизированы под быстрые GET.

### Синхронизация моделей
События — асинхронная проекция. После WorkoutCreated и ExerciseAddedToWorkout StatisticsProjectionService пересчитывает агрегаты; CacheInvalidationService удаляет устаревшие ключи. Допустима **eventual consistency** для статистики и справочника.

## 5. Реализация Event-Driven компонентов

### Инфраструктура
Docker Compose: Zookeeper, Kafka, Kafka UI, демонстрационное приложение (C++, POCO, librdkafka).

### Producer
После фиксации доменного изменения формируется объект события, сериализуется в JSON и публикуется в топик `fitness_tracker_events`. Ключ партиционирования — `user_id`.

### Consumer
Группа потребителей подписана на топик; каждое сообщение парсится, проверяется по event_id, вызывается обработчик типа события; offset подтверждается после успешной обработки.

### Тестирование
`make build && docker compose up -d` — демо публикует тестовые события; успешная обработка видна в логах контейнера и в Kafka UI (http://localhost:8081).

## 6. Примечание по терминологии
В RabbitMQ используются exchange и routing key. В Kafka аналоги: **топик** (канал) и **ключ партиционирования** (распределение по партициям). Потребление — через **consumer group**.
