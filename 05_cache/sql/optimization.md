## Q1: Поиск пользователей по маске ФИО

```sql
EXPLAIN ANALYZE
SELECT id, login, first_name, last_name
FROM users
WHERE (first_name || ' ' || last_name) ILIKE '%ария%'
ORDER BY login;
```

**До индекса GIN (pg_trgm):** последовательное сканирование `users`, фильтр по выражению, оценка стоимости растёт линейно с числом строк.

```
Seq Scan on users  (cost=0.00..N rows=...) (actual time=0.01..X ms rows=K loops=1)
  Filter: ((first_name || ' ' || last_name) ~~* '%ария%'::text)
```

**После `CREATE INDEX ... USING gin ((first_name || ' ' || last_name) gin_trgm_ops)`:** планер может использовать Bitmap Index Scan по GIN, снижая число проверяемых строк при больших объёмах.

```
Bitmap Heap Scan on users ...
  Recheck Cond: ((first_name || ' ' || last_name) ~~* '%ария%'::text)
  ->  Bitmap Index Scan on idx_users_fullname_trgm
```

**Вывод:** для подстрокового поиска без начала шаблона btree бесполезен; GIN + `pg_trgm` — рабочий компромисс (цена — размер индекса и стоимость обновлений при частых `INSERT`/`UPDATE` имён).

## Q2: История тренировок пользователя

```sql
EXPLAIN ANALYZE
SELECT w.id, w.name, w.workout_date, e.id, e.name, we.position
FROM workouts w
JOIN workout_exercises we ON we.workout_id = w.id
JOIN exercises e ON e.id = we.exercise_id
WHERE w.user_id = 'a0000001-0001-4001-8001-000000000002'::uuid
ORDER BY w.workout_date DESC, we.position;
```

**До индекса `(user_id, workout_date DESC)`:** часто `Seq Scan` на `workouts` с фильтром по `user_id`.

**После `idx_workouts_user_date`:** `Index Scan` или `Bitmap Index Scan` по префиксу `user_id` с уже отсортированным диапазоном по дате ускоряет выборку и упрощает соединение с `workout_exercises` (есть `idx_workout_exercises_workout`).

**Вывод:** составной индекс поддерживает и сценарий «история», и агрегаты за период (Q3).

## Q3: Статистика за период

Запрос из [queries.sql](queries.sql) (Q3) на больших данных выигрывает от того же `idx_workouts_user_date`: сначала сужается множество тренировок по `user_id` и диапазону дат, затем при необходимости подтягиваются строки `workout_exercises`.

## Q4: Частота использования упражнений

Агрегат с `GROUP BY` после `LEFT JOIN` на больших таблицах может использовать хеш-агрегацию. Индекс `idx_workout_exercises_exercise` помогает быстрее собрать строки по `exercise_id` при вложенных планах или merge join.

## Переписывание запроса (пример)

Если шаблон поиска **всегда** начинается с известного префикса (например, фамилия с первой буквы), условие можно заменить на `last_name ILIKE 'Пет%'` и использовать обычный btree по `last_name` (при подходящем индексе) вместо тяжёлого `%...%` по выражению. Для произвольной маски из варианта задания такой упрощение недопустимо — остаётся `pg_trgm`.

## Партиционирование (стратегия на рост данных)

Таблица `workouts` естественно растёт со временем. При миллионах строк имеет смысл **партиционирование по диапазону** `workout_date` (например, по месяцам): запросы статистики и истории с ограничением по дате будут затрагивать меньше партиций (partition pruning). Реализация: `CREATE TABLE workouts (...) PARTITION BY RANGE (workout_date)` и дочерние таблицы на каждый месяц/квартал; миграция с существующей непартиционированной таблицы — отдельный этап с переносом данных.

## Итог

- B-tree индексы: логин, связь тренировок с пользователем и датой, внешние ключи.
- GIN + `pg_trgm`: поиск по маске для ФИО и названий упражнений.
- Для проверки эффекта обязательно `EXPLAIN ANALYZE` на репрезентативном объёме и `ANALYZE` после массовых загрузок.
